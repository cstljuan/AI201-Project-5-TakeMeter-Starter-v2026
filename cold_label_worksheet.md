**Post text:** I'm not sure about why the accuracy is that far off in that particular game. Speculation: it kind of sounds like a game play decision to rush the player thinking they have much less time left than they got. Or who knows, it could just be bad programming/a rushed release. In general there's two ways you can count time that were feasible for these computer games: Counting CPU cycles taken to run instructions. For every assembler instruction there's a stated number of CPU cycles it will take to execute. And if you run the CPU system clock at a certain frequency, you'll know how long a cycle will take. One problem with this approach is that every slight programming change to the code used for counting time means the cycles will change and you have start over. That's every time you change something in the game during the development phase! So it is brittle and blunt, probably not used for things like in-game timers. Using an on-chip hardware timer. I think the MOS6502 CPU present in the NES had on-chip hardware timers. These can run while your program does other things, so they are greatly preferred. Even still, you will have to either interrupt your program on regular basis when the on-chip timer runs out (interrupt-based), which can be disruptive, or otherwise go check the timer when your program got the time for it (polling-based), which is less accurate. Even when using hardware interrupts, there is a built-in interrupt latency of a certain number of clock ticks while the CPU is loading your interrupt routine, which you have to take in account. Either way, your CPU clock cycle ticks or on-chip hardware timer ticks are derived from your system clock. And that one does not have better accuracy than what the oscillator component is specified to have. High accuracy oscillators are more expensive but drift less. For every single CPU cycle, your clock could potentially drift as far as the specified accuracy allows, so the inaccuracy adds up over time. So what the question really boils down to is what precision the oscillator on the NES had. It would be impossible for any program to achieve greater clock accuracy than that of the hardware. And that's a question far more suitable for retrocomputing.stackexchange.com.

## 18. Answer

**Post text:** In terms of ready-made things, I don't think there is a detailed distribution resource available for the distribution of the resources. I did find this resource on the wiki which lists minimum* resources per tree type . It is incomplete. * I don't think its the actual minimums, but instead an estimate for the minimum resources per tree. Still, it is a useful measurement if you want to estimate resources per sapling. The way to properly get the distribution of resources per sapling would be to use the feature definition of each type. The location of the tree feature definitions in the default Minecraft datapack is in data\minecraft\worldgen\configured_feature\* . You can learn what each field in these files so from this resource page in the wiki. Let's use the simplest example: birch trees. Here is the feature definition file, birch.json , in its full glory: { "type": "minecraft:tree", "config": { "decorators": [], "dirt_provider": { "type": "minecraft:simple_state_provider", "state": { "Name": "minecraft:dirt" } }, "foliage_placer": { "type": "minecraft:blob_foliage_placer", "height": 3, "offset": 0, "radius": 2 }, "foliage_provider": { "type": "minecraft:simple_state_provider", "state": { "Name": "minecraft:birch_leaves", "Properties": { "distance": "7", "persistent": "false", "waterlogged": "false" } } }, "force_dirt": false, "ignore_vines": true, "minimum_size": { "type": "minecraft:two_layers_feature_size", "limit": 1, "lower_size": 0, "upper_size": 1 }, "trunk_placer": { "type": "minecraft:straight_trunk_placer", "base_height": 5, "height_rand_a": 2, "height_rand_b": 0 }, "trunk_provider": { "type": "minecraft:simple_state_provider", "state": { "Name": "minecraft:birch_log", "Properties": { "axis": "y" } } } } } There is a lot of things we don't care about since they just indicate what types of block to use (which we know are birch leaves, wood, and dirt) or conditions that would otherwise limit the tree. We care about two particular fields: trunk_placer , and foliage_placer . trunk_placer : generates the logs according to the supplied pattern. In our case, this is straight_trunk_placer with arguments base_height=5, height_rand_a=2, height_rand_b=0 . From the wiki, this means that a random value between 0 and 2 is added to the trunk height. Since this is the simplest trunk type, we can easily conclude that there is a 33% chance to get a tree with 5, 6, or 7 logs respectively. foliage_placer : generates the leaves according to the supplied pattern. In this case, we got blob_foliage_placer with arguments height=3, offset=0, radius=2 . This generates a maximum blob with a maximum leaf count of (height-1)*(radius*2+1)^2+2*(radius*2-1)^2-4=64 . There is no exact documentation on how the corner leaves are randomly placed but we can assume there is a uniform random distribution in the leaf count (please correct me if the source code says otherwise). The minimum count for blobs is assumed to be the max minus height*4 leaves. So we get that the distribution of leaves in birch would be uniform between 52-64 leaves You can go over the rest of the tree types using the feature definitions to get a rough idea of the distributions, or honestly just use the wiki resource to get an approximate count
